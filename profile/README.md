<p>住宅 IP 池这个说法本身就有误导性。很多人以为「买个大池子，几十个号从里面随便取，就等于天然隔离」，结果号一多就成片出问题。问题不在池子本身，在四个被反复传播的错误认知上。这篇把它们逐条摊开，说清「听起来对、实际上错在哪」，再给纠正后的做法。文中判断依据是一般实践，规模不同结论会有偏差，仅供参考。</p>
<h2>一、误区一：池子越大越安全</h2>
<p>这是流传最广的一条。逻辑听起来顺：池子大，每个 IP 被用到的次数少，重复率低，自然更干净。但池子大只解决了「重复率」，没解决「归属分散」和「行为混杂」这两件事。</p>
<h3>大池的真实代价是不可控</h3>
<p>一个几千条地址的池子，你无法知道某一条今天被谁用过、用来做什么。取到一个昨天刚被高频使用的地址，表现不会比小池子好，甚至更差。可控性的价值往往高于绝对数量。</p>
<h3>池子大不等于独享</h3>
<p>池子是共享资源，即便总量大，你拿到的仍是「非独占」的一段。几十个号从同一个池取地址，只要池子的分配逻辑不做用户级隔离，仍可能出现两个号落到同段的情况。真正解决问题的是「一号一段」的独占，而不是池子的规模。</p>
<h2>二、误区二：换了 IP 就等于换了环境</h2>
<p>很多人的操作是：发现异常，换一条 IP，重启浏览器，再登录。这套动作只改了出口，环境里的东西一点没动。</p>
<h3>环境包含什么</h3>
<p>容器指纹、时区、语言、分辨率、字体、Cookie、本地存储、缓存。换 IP 只动了其中一项的外部对应关系，其余七项原封不动。所以换完仍然是「同一台机器、同一张脸，只是从另一个门进来」。</p>
<h3>正确的关系是配对</h3>
<p>出口和环境应该是一对一配对的，一个号一套。换的时候要么一起换，要么都不换。只换一半，等于制造了一个「从未出现过的新组合」，反而更不自然。</p>

<h2>三、误区三：装了指纹浏览器就万事大吉</h2>
<p>工具解决的是「能不能隔离」，配置解决的是「隔离得对不对」。装了工具但所有 Profile 用默认参数，等于给每个号发了一张一模一样的身份证。</p>
<h3>默认参数是最常见的坑</h3>
<p>新建 Profile 时如果不改时区、语言、分辨率，所有容器都会继承宿主机的设置。表面上每个号有独立容器，实际上八项参数里有六项相同。这种情况比不隔离更难发现，因为你以为已经隔离了。</p>
<h3>建议的做法是建模板再改差异项</h3>
<p>先建一个与出口城市匹配的模板，包含时区、语言、分辨率、字体档位；每个号从模板克隆，只改账号相关的项。这样一致性有保证，差异也落在合理区间内，不会出现某个号明显与众不同。</p>

<h2>四、误区四：号多就得共用一个池省钱</h2>
<p>这条在预算紧张时特别容易被接受。但把账算完整会发现，共用池省的是线路费，赔的是排查时间和账号折损。</p>
<h3>故障扩散的代价</h3>
<p>共用池时，一条线被牵连，挂在它上面的号一起受影响。你没法判断是哪个号引起的，只能全部停下来查。按人天折算，一次集中排查的成本往往超过多买十几条独享线的月费。</p>
<h3>折中的切分方式</h3>
<p>不是所有号都需要独享。可以按三档切：主力号一条线一个号，一般号两号一条线但错开时段，试验号继续用池子。切分之后，主力号出问题不影响一般号，试验号出问题直接弃掉，影响面被限制在最小。</p>
<h2>五、纠正之后的具体做法</h2>
<p>把上面四条反过来，得到一套可执行的做法。核心只有一句：一个号对应一条出口、一套环境、一份记录。</p>

<h2>常见问答</h2>
<h3>共享池真的完全不能用吗？</h3>
<p>答：能用，要看用途。试验号、临时验证、非关键任务用共享池完全合理，成本低且够用。不能用的是把它当成主力号的基础设施，那等于把最重要的资产放在最不可控的资源上。</p>
<h3>几十个号必须几十条线吗？</h3>
<p>答：不一定，但主力号需要。按三档切分后，通常主力号占三到五成，这部分必须独享；其余可以复用。全独享是理想状态，按档位分配是现实状态，两者不矛盾。</p>
<h3>怎么发现自己的 Profile 参数雷同？</h3>
<p>答：抽两个容器做指纹检测，逐项比对。时区、语言、分辨率、Canvas 哈希、WebGL 渲染器五项里，如果有三项以上相同，基本可以判定雷同。这个检查建议每月做一次，尤其在新加号之后。</p>
<h3>已经按共用池跑了一段时间，怎么迁？</h3>
<p>答：分批迁，不要一次全动。按主力号优先的顺序，每次迁三到五个，迁完观察三天，稳定再迁下一批。迁移期间保持两条路径并行，任何时候都能回退。</p>
